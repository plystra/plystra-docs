## Start Here

If you are adding Plystra to an existing backend, start with the Developer Handbook. It gives you the concrete object model, API calls, credential choices, security boundaries, SDK examples, and backend guard flow for the full path:

```text
register resource type -> create Space and identities -> grant role -> register resource -> call authz/check
```

## What Plystra v1.0 Covers

<CardGrid stagger>
	<Card title="Explainable identity" icon="approve-check-circle">
		Every authorization decision explains the `User -> UserMember -> Member -> Space` path that acted.
	</Card>
	<Card title="Scoped permissions" icon="setting">
		Permissions are evaluated against `self`, `group`, `group_tree`, and `space` scope rules. `global` is reserved and disabled in v1.0.
	</Card>
	<Card title="Resource Registry" icon="document">
		Resource types, actions, mappings, risk levels, and audit defaults are stored as governed metadata.
	</Card>
	<Card title="Append-only audit" icon="open-book">
		Allow and deny decisions write trace snapshots that remain readable after metadata changes.
	</Card>
	<Card title="Self-hosted Core" icon="rocket">
		PostgreSQL, versioned migrations, Ent schema checks, Docker Compose, and production safety guards are part of the Core.
	</Card>
	<Card title="Protected API surface" icon="lock">
		Non-public Core APIs require the Bearer user session with an active admin grant. Data Console and metrics are disabled by default.
	</Card>
</CardGrid>
